SECTION 0 — WHAT ANTEX IS
--------------------------------------------------------------------------------
Antex is a vibe-coding agent product: a web app where a user types an idea and a
real AI agent builds it — reading and writing real project files, generating real
images, running real commands through a real execution provider, and reporting
honestly when something is not available.

Product name is always written exactly "Antex".

Stack: TanStack Start v1 (React 19, Vite, Tailwind v4, shadcn/ui), backend on
Lovable Cloud (Supabase: auth, Postgres with RLS, storage), server logic in
createServerFn, Replit Cloud execution is used for remote/cloud execution.

SECTION 5 — NEW REQUIREMENT: MY OWN GEMINI KEYS, NO AI GATEWAY
--------------------------------------------------------------------------------
Remove every Lovable AI Gateway implementation: the gateway base URL, the
LOVABLE_API_KEY usage, the live model catalog (listModels), the model picker
component, the model-choice popup, the stored default_model preference, and all
"choose a model" UI. No model selection is exposed to the user anywhere.

I will provide 4 Gemini API keys. Here's what's important:

  - When a model exhausts its requests/day, fall back to the next model, and so
    on. Do this from the BEST model to the WORST model.
  - After every model on one API key has its requests/day exhausted, fall back to
    the next API key. Do this for all 4 keys.
  - Only when all models on all 4 keys are exhausted, show a single clear message
    saying the quota is exhausted.

Implementation notes for this behaviour:
  - Keys live as server-side secrets GEMINI_API_KEY_1..4, never in client code.
  - Model chain, best -> worst, tried in order on each key.
  - Treat HTTP 429 and RESOURCE_EXHAUSTED as "this model/key is out": advance to
    the next model, then the next key; never retry the same pair in a loop.
  - Any other error is a real error and must be surfaced honestly, not swallowed
    as a quota fallback.
  - No artificial timeouts around a generation call; stream where possible.
  - The message stored per turn records which model and which key slot actually
    served it, so failures are traceable.

--------------------------------------------------------------------------------
8.2 GEMINI MODEL + API-KEY FALLBACK SYSTEM
--------------------------------------------------------------------------------
The approved fallback system is a two-dimensional fallback chain.

Dimension 1: models on the current API key.
Dimension 2: API keys 1 through 4.

The model ordering must be BEST → WORST according to the configured model policy.
Do not invent a model ranking. The implementation must use only models that are
actually available to the configured Gemini API environment.

For API key 1:
  best compatible model
  ↓ if requests/day quota is exhausted
  next compatible model
  ↓
  next compatible model
  ↓
  ...
  ↓
  if every compatible model on key 1 is exhausted
  KEY 2

Repeat the same process for keys 2, 3 and 4.

If all compatible models on all four keys are exhausted, return one clear quota
exhaustion state to the user.

Never repeatedly retry a known exhausted model/key pair.

Quota exhaustion signals such as HTTP 429 or a provider response equivalent to
RESOURCE_EXHAUSTED should advance the fallback chain when the response actually
indicates quota/rate exhaustion.

Do not classify every error as quota exhaustion.

Invalid API keys, invalid requests, unsupported models, malformed responses,
network errors, provider outages and other errors need their own handling.

The system must never silently turn an authentication failure into an endless
fallback loop.

The actual model/key slot that served each successful request should be recorded
as safe metadata. Never record the secret value.

--------------------------------------------------------------------------------
8.3 GEMINI MODEL DISCOVERY
--------------------------------------------------------------------------------
If dynamic model discovery is used, discover models from the actual configured
Gemini API rather than maintaining a fake hard-coded catalog.

Filter the catalog to models that can actually perform the operation requested.
For example, a coding/agent request may require text generation and tool/function
calling capabilities.

A model that cannot perform a required capability must not be selected merely
because it is present in a catalog.

Do not claim support for a model that the current credentials/environment cannot
actually use.

8.6 HYBRID EXECUTION — WEB + DESKTOP + ANDROID
--------------------------------------------------------------------------------
The approved architecture is hybrid.

UNIFIED EXECUTOR
├── GitHubActionsExecutor
├── LocalDesktopExecutor
└── LocalAndroidExecutor

WEB:
  Replit Cloud is the approved execution/build provider.

DESKTOP:
  Local CPU, local filesystem and local processes are preferred.

ANDROID:
  Local CPU/execution can be used when the device and runtime support the task.
  Replit Cloud can be used as a fallback when connected and when local
  execution is unsuitable.

The rest of Antex must depend on the Executor interface, not a single provider.

Conceptual interface:
execute(command)
readFile(path)
writeFile(path, content)
listFiles(path)
createDirectory(path)
deletePath(path)
movePath(source, destination)
startProcess(command)
stopProcess(process)
getProcessOutput(process)

The implementation may use different transport/mechanisms on each platform.

CURRENT EXECUTION ARCHITECTURE — REPLIT CLOUD + LOCAL CPU
--------------------------------------------------------------------------------
Antex uses a platform-independent execution layer with two primary modes:

1. Replit Cloud — Web / Cloud Execution
   Web-based and remote development tasks run in the Replit Cloud Linux
   environment. Commands, filesystem operations, dependency installation,
   builds, tests, processes, logs, stdout, stderr, and exit codes must be real.
   Never simulate execution or report an operation as completed when it was not.

2. Install Locally — Use Local CPU
   Antex can be installed locally on supported desktop and mobile platforms.
   Where supported, development tasks run directly on the user's own CPU and
   local filesystem/workspace. Commands, builds, tests, and processes are real
   local operations; no cloud execution is required for tasks the local platform
   can perform. The local runtime is integrated into Antex and does not require a
   separate terminal application.

3. Executor routing
   WEB / CLOUD -> Replit Cloud Linux
   DESKTOP -> Local CPU
   ANDROID -> Local CPU where supported; Replit Cloud fallback where appropriate

4. Common executor capabilities
   execute, readFile, writeFile, listFiles, createDirectory, deletePath,
   movePath, startProcess, stopProcess, getProcessOutput.

5. Android local builds
   Warn that demanding local builds can consume CPU, RAM, storage, battery, and
   thermal capacity. Offer cloud execution for workloads better suited to it.

6. The project filesystem remains the source of truth in both execution modes.
